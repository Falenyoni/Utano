### Backend RBAC enforcement — design (finalized 2026-07-31, not yet built)

**The corrected mental model, per Bongani's direction:** RBAC should be *flexible per practice* — any role, system or custom, can have its permissions freely edited by whoever is authorized to manage roles (`settings.roles`, or Admin by default). The gate belongs on **who is acting**, not on **which role is being touched**. This corrects the original #2 fix, which locked system roles' *permissions* as platform-owned — that was solving the wrong layer. What actually needed to be built was authorization enforcement (#1) in the first place; #2 becomes a byproduct of #1 rather than a separate concern.

**What stays locked on system roles, and why:** only the **name**. Renaming was explicitly ruled out ("No Renaming") because `IModuleDescriptor.GetPermissionsForRole(roleName)` — and any future reconciliation — is keyed on it. Since renaming is blocked at the API layer, `(PracticeId, Name, IsSystem = true)` is now a fully reliable, permanent key for that purpose — already backed by the existing unique index. **No new column, no hidden "marker permission," no schema change needed** — that was considered and correctly rejected as solving a problem the rename lock already solves. `RoleId` itself can't serve this purpose (it's a per-row surrogate key, unique per practice — "Admin" in two different practices has two unrelated `RoleId`s, so it can't be the cross-practice "role type" identifier `GetPermissionsForRole` needs).

**The enforcement mechanism to build:**
1. `IRequirePermission` (Core) — `string Permission { get; }`. Commands/queries implement it to declare what they need.
2. `PermissionAuthorizationBehavior<TRequest,TResponse>` (Core) — a MediatR `IPipelineBehavior` that checks `currentUser.HasPermission(...)` for any request implementing `IRequirePermission`, before the handler runs. Registered **once**, in `Utano.API/Configuration/AppConfiguration.cs` (`services.AddTransient(typeof(IPipelineBehavior<,>), typeof(PermissionAuthorizationBehavior<,>))`) — applies globally across every module's MediatR pipeline regardless of which module's `AddMediatR` call registered the handler, since it's one shared DI container.
3. `UtanoForbiddenException` (Core, new) — a permission denial is a 403, not a 400. `GlobalExceptionHandler` needs a new branch mapping this to `403 Forbidden` (currently only handles `UtanoDomainException` → 400 and everything else → 500).
4. First real usage: `UpdateRoleCommand`/`CreateRoleCommand` implement `IRequirePermission` with `Permission => "settings.roles"`. This is the natural first target given it's what triggered this whole design conversation. Every other module's commands get the same treatment incrementally after this — systematic, module-by-module, not a big-bang rewrite (per the original Tier 1 sizing note).

**Revised `UpdateRoleHandler` (corrects the 2026-07-30 fix):**
- Remove the system-role permission-editing lock entirely — any role's permissions become freely editable once `PermissionAuthorizationBehavior` has confirmed the caller holds `settings.roles`.
- Keep the system-role **name** lock as-is.
- Replace the hardcoded `role.Name == SystemRoles.Admin` deactivation check with the real invariant: **the practice must never end up with zero active roles holding `settings.roles`.** Compute this by checking whether the role being saved will still grant `settings.roles` after the update, and if not, count other active roles in the practice that do — block if that count is zero. This correctly protects against deactivating Admin, stripping `settings.roles` from Admin, *or* deactivating some other custom role that happens to be the practice's only role-manager — not just the one hardcoded name.
- `CreateRoleHandler` needs no equivalent check — creating a role never removes anyone's access.

**Reconciliation (Tier 2, #4/#5) stays additive-only** regardless of this — it only ever inserts a permission a role doesn't already have; it never re-adds something a practice deliberately removed, since there's no way to distinguish "never had it" from "removed on purpose" without extra bookkeeping that isn't being built. No conflict with per-practice permission customization.
